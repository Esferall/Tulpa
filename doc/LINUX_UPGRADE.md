# Linux：保留数据升级

使用多实例时，先在主目录运行 `./tulpa instances list`，逐个执行
`./tulpa instances stop <ID>` 停止子实例；主后台停止不会替你关闭独立的子实例服务。
然后停止本安装目录的主后台：

```sh
./tulpa stop
```

这也会停止本实例托管的 SL；Docker 的持久数据卷会保留。退出 TUI 本身不会停止后台。

## 备份

确认后台已停止后，备份当前目录中的 `data/`、`imports/`、`exports/`、`.env`（存在时），
以及自己新增或改过的人格卡和配置文件。备份用于自己恢复，不应发给其他测试者。
多实例还要备份 `instances/` 中各实例的数据、配置和人格卡，以及主目录的
`data/instances.json`；不需要备份各子目录的 `.venv` 依赖链接。

`data/snowluma-managed/` 中的凭据密文和本机密钥要一起保留。
MCP 授权、学习记录、表情资料和记忆应随整个 `data/` 迁移；只复制部分文件会丢失关联。
Docker 数据卷保存在 Docker 引擎中，项目目录的备份不等于卷备份。

## 同目录更新

1. 将新测试包解压到一个临时目录，检查其中没有 `data/`、`.env` 或账号配置。
2. 把新包中的源码文件复制到原安装目录，保留原来的数据、配置与可选组件缓存。
   自改的同名人格卡先另存，再决定是否采用新版预设。
3. 运行 `./tulpa`。启动器会补齐当前运行依赖，然后启动后台和界面。
4. 核对 SL 账号与授权群，再让外部 Agent 重连 MCP。需要新版人格时停止旧会话并重新创建。
5. 在「实例管理」重新启动子实例：启动器会从主目录同步公开源码，保留各自的数据、
   配置和已存在的人格卡。没有停止的子实例继续运行旧代码，直到你显式停止并重启。

如曾安装用户 systemd 服务，检查 `./tulpa service status`。
服务绑定安装路径和端口；迁移目录后应从新目录重新安装。已有同名服务属于其他目录时，
先在原目录执行 `./tulpa service uninstall`，再在新目录执行 `./tulpa service install --start`。
不要把原 `.venv/` 当作可跨机器迁移的运行环境，新主机应重新安装依赖。
多实例的注册信息、依赖链接及 SL 所有权包含安装路径，当前应使用同目录更新；
直接移动 `instances/` 不会自动重定位记录或接管旧 Docker 容器。

## 更换机器

QQ / 微信客户端、源数据路径、系统权限和 Docker 环境都需要在目标机器重新核对。
SL Docker 托管记录还绑定原 Docker 引擎和数据卷；只复制项目文件不能直接恢复容器，
可在新机重新配置并扫码。先保留旧机备份，确认新机读取与连接正常后再处理旧环境。

遇到升级问题时，停止后台并用备份恢复源码和整套数据；不要用旧代码直接尝试写入已变更的数据格式。
测试反馈请附系统、架构、版本和脱敏错误，见 [安全报告](SECURITY.md)。
